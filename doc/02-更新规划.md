## 1. 规划控制、冻结规则与当前基线

### 1.1 当前项目定位

星序的完整名称继续使用“星序——虚拟仿真实验室模拟”。它首先是一组具有真实操作、动画反馈和学科模型的虚拟实验，其次才是承载学生、教师、管理员协同的教学平台。

面向毕业设计、多媒体类竞赛和教学工具类赛事时，评审最容易直接观察的价值依次是：

1. 实验是否一眼可懂、立即可操作并有明显反馈；
2. 动画是否表达真实变量、过程、比较和结论；
3. 学科内容是否足够丰富，重点实验是否具有记忆点；
4. 学生和教师是否能通过清楚的入口发现、使用和管理实验；
5. 班级、课程、作业和学习结果是否真实连通；
6. 架构是否能解释 Web 端、未来小程序端和统一后端的关系；
7. 演示包、论文图、讲解脚本和现场恢复方案是否完整。

后台加密、极限性能、微服务拆分、生产级对象存储和超高可维护性不是当前竞赛主线。已有安全、权限和数据一致性能力不得破坏，但新增投入必须优先回答：“学生、教师或评委能直接看到什么改善？”

### 1.2 本轮必须遵守的九条硬门禁

1. **冻结既有实验**：当前 124 项实验/活动的既有路由、首屏、布局、视觉、交互、动画、参数、求解器和返回关系默认禁止修改。
2. **禁止新增课程化包裹**：不得在既有实验入口或学生工作台前新增长篇课程正文、学习旅程卡、内容块说明、包哈希、版本摘要或强制检查点。本轮以前已存在的目录短文案不在还原阶段擅自批量修改；与本规则冲突的历史入口统一列入负责人审阅项。
3. **实验首屏可操作**：进入实验后，核心画面和主要控制必须在第一视口直接可见，不得先阅读大段说明才能操作。
4. **只增不改**：扩充内容时优先新增独立实验、独立页面、独立模块或独立展示入口，不改写已完成实验。
5. **知识纠错先审批**：发现事实、公式、单位、模型或教学表述错误时，只能先记录证据、影响范围和拟修改内容；项目负责人批准后才可修改。
6. **平台不得喧宾夺主**：班级、课程、作业、进度和教师管理只在实验外提供发现、组织、布置、回读与跳转，不得改变实验本身的操作节奏。
7. **例外必须逐项批准**：任何触及受保护实验文件、路由或视觉的改动都要列出文件、截图、理由和回退方式，经项目负责人单独确认。
8. **规划通过才开工**：项目负责人已于 2026-08-24 明确恢复目标并允许开发；后续仍必须按本文版本顺序和待决门禁执行。
9. **不得用重构冒充成果**：目录整理、框架迁移、抽象层增加和后端精修只有在直接阻断可见成果时才进入当前版本。

## 2. 纠偏后的全局开发审查

### 2.1 首要结论

此前最严重的方向错误，不是技术实现失败，而是把“实验平台”误写成了“课程阅读平台”。在机械能守恒等页面周围加入大量课程目标、内容块、来源、检查点和版本说明，虽然能展示内容平台能力，却直接压缩了实验画面、延迟了操作、打断了原有节奏，也让成熟实验显得像课程正文中的一个附件。

纠偏后的判断是：

- 既有实验不需要被统一成同一种课程外壳；
- 平台价值应通过导航、班级组织、任务布置和结果回读体现；
- 实验价值应通过画面、控制、反馈、模型和可重复操作体现；
- 二者可以共享身份和数据，但不能共享同一套强制页面结构；
- 内容建设的主要新增量应落在新实验，而不是重写旧实验。

### 2.2 从中学教师视角看

中学教师最关心的不是后台有多少表，而是能否在课堂上迅速完成“找到实验—投屏操作—改变变量—观察现象—让学生回答—继续讲课”。当前项目的优势是实验数量和题材丰富，班级业务也已成立；主要问题是：

1. 实验入口与教师工作台之间的关系不够直接；
2. 教师需要自己判断哪个实验适合课堂演示、学生自探究或课后任务；
3. 重点实验缺少统一但轻量的展示标签，如预计用时、适用场景、主要变量；
4. 教师工作台信息很多，但“现在最该做什么”不够突出；
5. 竞赛演示时无法用一条短路径展现“教师选实验—布置—学生操作—教师回读”。

优化方向不是给实验加长篇教案，而是在实验外提供：课堂演示筛选、快速启动、任务关联、学生结果摘要和返回班级的清楚入口。

### 2.3 从中学学生视角看

学生判断一个实验好不好，通常只用几十秒：画面是否吸引、能否立刻动手、操作后是否有反应、错误是否能理解。当前主要问题是：

1. 星系、学科、课程、活动和工作台层级较多，入口语义不总是一致；
2. 部分列表和管理信息会与实验主动作争夺注意力；
3. 实验之间的精品程度差异较大，学生可能先遇到普通页面而不是最佳作品；
4. 移动端虽然能用，但部分复杂页面的首屏焦点仍不稳定；
5. “完成”“进度”“回执”等词汇有时偏系统语言，而不是学生语言。

优化方向是让学生更快进入实验、减少实验外的选择负担、在目录中突出视觉和操作特征，并让完成回执只说明真正有用的下一步。

### 2.4 从本科毕业导师和竞赛评委视角看

导师或评委会追问三个层次：作品做了什么、为什么这样设计、技术是否支撑真实业务。星序已经具备较强的第三层基础，但第一层的展示与第二层的设计解释仍不够集中。

主要问题是：

1. 124 项活动数量可观，但缺少一组明确的新增精品实验作为本轮成果峰值；
2. 业务能力分散在多个工作台，短时间内不容易形成完整故事；
3. 架构图、业务图、数据流图和实验运行时图没有组成统一论文叙事；
4. 页面真实能力强于演示脚本，现场仍依赖开发者临时解释；
5. 内容平台底座虽然有技术含量，但若不能转化为可见价值，就不应成为主要开发投入；
6. 恢复、降级、离线包和固定演示数据仍需要最终封装。

优化方向是用少量高质量新增实验、清楚的师生协同路径和完整交付材料，把现有技术深度显性化。

### 2.5 前端内容深度的真实问题

| 问题 | 当前表现 | 新的处理方式 |
| --- | --- | --- |
| 精品密度不均 | 少数实验明显强，普通活动缺少记忆点 | 新增精品实验，不批量改旧实验 |
| 目录表达偏功能清单 | 卡片能进入，但难以看出操作特色 | 在实验外补充轻量标签、动图或缩略预览 |
| 工作台偏管理面板 | 表格、数字和状态多 | 突出一个主动作和少量关键事实 |
| 层级语义不稳 | 星系、课程、活动、工作台来回切换 | 统一外层导航和返回上下文 |
| 竞赛故事分散 | 需要开发者口头串联 | 建立可重复的三分钟和十分钟路径 |
| 移动首屏焦点不稳 | 有些页面信息密度高 | 只优化外层容器和新模块，不改旧实验布局 |

### 2.6 后端业务逻辑仍值得保留的深度

当前后端不是简单空壳。它至少已经覆盖以下真实层次：

1. **身份层**：会话、用户、学生、教师、管理员；
2. **组织层**：学校、学校成员、班级、班级成员和加入流程；
3. **教学层**：课程、单元、班课绑定、发布计划、作业和提交；
4. **学习层**：学习事件、权威证据、完成投影、恢复和教师回读；
5. **内容层**：内容草稿、版本、审批、发布与回滚基础；
6. **治理层**：管理员范围、审计、异常、任务和组织管理；
7. **交付层**：Alembic、SQLite 演示数据、同源启动和测试合同。

这些层次足以支持毕业论文中的领域建模、作用域权限、状态流转、版本化内容和多端 API 设计。当前不应为了“更像大型系统”继续增加低可见复杂度。

### 2.7 后端当前主要问题

#### 问题一：作用域正确，但用户语言过于技术化

全局角色、学校成员、班级成员、课程协作者和发布范围共同决定权限，这是合理的；问题在于前端常把它压缩成“三级用户”，或者直接暴露技术状态。

**规划处理**：保持服务端作用域，不新建第二套角色等级；在外层页面转换成“我所在的班级、我可管理的课程、我需要处理的事项”。

#### 问题二：业务接口完整，但页面需要拼装过多

班级、课程、作业、进度和证据接口分别成立，一个工作台首屏却可能需要多个请求和多次排序，容易出现加载跳变和空态不一致。

**规划处理**：只为明确可见页面增加薄聚合读取；底层写接口保持原样，不另建 BFF 或微服务。

#### 问题三：内容版本能力容易反向支配实验体验

草稿、版本、发布包和班级固定版本具有技术价值，但不代表所有实验必须显示版本信息或进入统一内容块页面。

**规划处理**：内容平台只管理“谁能看、哪个版本、如何布置和如何回读”；实验运行时继续由实验 owner 自己负责。

#### 问题四：旧学习状态与权威证据并存

旧进度路径和新证据路径同时存在，新增页面若不明确读取边界，容易重复计算或出现两个完成状态。

**规划处理**：不做全量数据重写；新外层页面优先读取权威投影，旧路径只保留兼容，具体合并问题在影响可见页面时逐项解决。

#### 问题五：部分 owner 过大

教师、管理员、学习证据和大型页面脚本认知成本较高，但它们目前可以工作。

**规划处理**：只在新增可见功能触碰时局部抽离，不开展全仓重构。

#### 问题六：Web 与未来小程序需要稳定边界

未来主服务器同时服务 Web 和微信小程序时，浏览器 Cookie 会话、页面专用 DTO 和静态资源路径不能直接等同于小程序客户端合同。

**规划处理**：当前只保证领域 service 和 `/api/v1` DTO 客户端中立；小程序鉴权、上传、离线缓存和原生实验运行时全部留在长期方向。

### 2.8 当前最不值得投入的事项

- 为没有现实风险的本地演示继续叠加额外加密层；
- 为竞赛现场规模开展极限并发和压力优化；
- 把模块化单体拆成微服务；
- 全量重写 Vanilla SPA；
- 为追求目录美观拆解所有大型 owner；
- 把 124 项旧实验批量迁入统一课程模板；
- 给所有普通实验增加形式化学习证据状态机；
- 在小程序尚未立项时提前维护两套前端实现。

## 3. 新的系统层级与修改边界

### 3.1 纠偏后的总体架构

~~~mermaid
flowchart TB
    GUIDE[作品导览与实验发现] --> CATALOG[三星系实验目录]
    STUDENT[学生工作台] --> CATALOG
    TEACHER[教师工作台] --> CATALOG
    ADMIN[管理员治理台] --> PLATFORM[学校 / 班级 / 课程治理]

    CATALOG --> OLD[既有 124 项实验\n冻结保护]
    CATALOG --> NEW[新增实验模块\n独立路由与 owner]

    OLD --> RUNTIME[现有实验运行时 / 求解器 / 动画]
    NEW --> NRUNTIME[新增实验运行时 / 模型 / 动画]

    STUDENT --> API[/FastAPI 领域 API/]
    TEACHER --> API
    ADMIN --> API
    API --> DOMAIN[学校 / 班级 / 课程 / 作业 / 学习结果]
    DOMAIN --> DB[(SQLite 演示 / 未来正式数据库)]

    RUNTIME -.可选学习结果.-> API
    NRUNTIME -.可选学习结果.-> API
~~~

关键关系是：目录负责发现，实验负责操作，平台负责组织，后端负责事实。任何一层都不能用自己的结构覆盖另一层的核心体验。

### 3.2 既有实验保护层

受保护范围包括：

- `pages/physics`、`pages/chemistry`、`pages/mathematics`、`pages/biology`、`pages/algorithms` 等既有实验 owner；
- `pages/frontier`、`pages/engineering` 等未来星系既有互动 owner；
- 实验注册表中的既有 key、路由、标题、返回关系和资源加载顺序；
- 现有 Canvas、SVG、Three.js、GSAP、DOM 动画和求解器；
- 现有默认参数、控制件、数据输出、模型边界和实验内说明；
- 已经建立的学习证据事件顺序和服务端完成规则。

保护不等于永远不能修复错误，而是任何修改都必须从“默认允许”改为“有证据、有范围、有截图、有回退、先批准”。

### 3.3 新增实验扩展层

新增实验使用独立目录、独立 owner 和独立注册项，不复制或重命名旧实验。建议结构如下：

~~~text
pages/<subject>/<new-experiment>/
├── index.js              # 页面生命周期与事件接线
├── model.js              # 学科模型或求解器
├── renderer.js           # Canvas / SVG / Three.js / DOM 画面
├── styles.css            # 仅作用于新实验命名空间
├── manifest.js           # 标题、标签、路由、资源和展示信息
└── assets/               # 新实验独占素材
~~~

首批新增实验不强制全部拆成六个文件；小实验可以合并，但必须满足：

1. 新 key 不与 124 项既有活动冲突；
2. 新 CSS 不泄漏到旧实验；
3. 新路由不替换旧路由；
4. 新资源不修改旧资源内容；
5. 页面具有显式初始化和销毁；
6. 第一视口可以操作；
7. 主要变量、单位和模型边界可解释；
8. 键盘、触屏、减少动态效果和基本响应式有明确降级；
9. 失败时能关闭或移除新注册项，不影响旧目录。

### 3.4 实验外的平台层

平台层可以做：

- 搜索、筛选、收藏、最近使用和重点实验推荐；
- 班级课程中的实验关联与快速启动；
- 教师布置实验任务、设置截止时间和查看结果；
- 学生查看待完成实验、最近实验和完成回执；
- 管理员查看学校、班级、课程和内容治理事实；
- 作品导览、演示路径和竞赛展示模式。

平台层不可以做：

- 在进入旧实验前强制阅读课程正文；
- 在旧实验上方或旁边插入大块课程旅程；
- 为显示技术深度暴露 schema、package hash、内部 ID 或发布 revision；
- 把原实验控制面板压缩成课程卡片的一小部分；
- 通过 iframe 或二次容器改变旧实验响应式尺寸；
- 以“统一风格”为由重写全部实验。

### 3.5 后端与双端协同边界

~~~mermaid
flowchart LR
    WEB[Web SPA] --> DTO[/稳定 API DTO/]
    MINI[未来微信小程序] --> DTO
    DTO --> SERVICE[领域 Service]
    SERVICE --> ACCESS[身份与作用域]
    SERVICE --> CLASS[班级 / 课程 / 作业]
    SERVICE --> LEARN[进度 / 证据 / 回读]
    SERVICE --> CONTENT[内容与发布版本]
    ACCESS --> DB[(统一数据库)]
    CLASS --> DB
    LEARN --> DB
    CONTENT --> DB
~~~

当前阶段只要求：新 API 不依赖 DOM、浏览器路由或页面模板；领域规则落在 service，而不是复制在 Web 页面。小程序登录态、媒体上传、原生动画适配、分享卡片和审核规则不在本轮实现范围。

### 3.6 论文技术解析层级

毕业论文可按以下层次解释系统，而不需要新增复杂架构：

1. **产品层**：三星系实验内容与三角色教学协同；
2. **交互层**：实验即时操作、画面反馈、外层发现和任务回读；
3. **前端运行层**：Router、PageRegistry、实验 owner、生命周期与按需资源；
4. **业务层**：学校、班级、课程、作业、提交、学习证据和内容版本；
5. **数据层**：SQLAlchemy 模型、Alembic 迁移、SQLite 演示与未来数据库边界；
6. **质量层**：合同测试、pytest、浏览器双视口、console、缓存代际与回退；
7. **扩展层**：新增实验插件式接入和未来 Web/小程序共用后端。

### 10.3 开发难度心理预期

- **最低风险**：文档、演示脚本、外层标签、固定演示数据和缓存恢复；

- **最高风险**：新增实验的科学模型、实时动画、跨设备交互和素材质量；
- **不值得承担的风险**：旧实验大规模改版、全仓框架迁移、微服务拆分和小程序提前实现。

## 11. 长期方向：记录但暂不启动

### L1. Web + 微信小程序双端协同

规划 HTTPS、域名、反向代理、MySQL/PostgreSQL、备份、监控和迁移演练。当前本地展示不因此阻塞。

### L4. O2O 翻译适配

建立稳定文案 key、术语表、长文本布局和资源本地化，不在当前内容建设中顺手翻译。

### L5. 正式在线判题系统

需要隔离 runner、资源限制、任务队列和失败降级；当前代码空间保留现有诚实边界。

### L6. AI 学习与教学助手

学生、教师、管理员必须分开设计；任何权威写入需要人工确认、权限和审计。当前不启动。

### L7. 真实课堂实证

在作品稳定后设计知情、样本、任务、指标和反馈流程；开发者自测不能冒充实证研究。

### L8. 企业级安全、性能和运维

真实公网部署时再补充威胁建模、密钥管理、速率限制、压测、可观测性和灾备，不作为当前竞赛主线。

### L9. 历史星系接入

当前只保留命名空间和文档预留；必须获得真实代码、清单和验收材料后才能进入目录。

### L10. 全量前端框架迁移

只有当前 SPA 明确阻断新功能、团队规模或长期维护时才评估；本轮不做。
