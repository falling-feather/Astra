## 0. 全局总览与硬规则

### 0.1 本轮一句话目标

在不大改已有实验的前提下，把现有“能登录、能建班、能建课、能布置和提交”的后台骨架，建设成用户能够直接理解和操作的完整教学平台：

`教师申请 → 管理员批准 → 教师创建课程 → 管理员审核课程信息 → 学生申请加入 → 教师批准 → 学生学习 → 教师发布新内容 → 学生提交 → 教师批改 → 学习结果回读`

### 0.2 当前开发顺序

1. `V8.3.3`：已完成本文重构和 UML 设计门禁。
2. `V8.3.4`：已完成机械臂逆运动学，并冻结其他新实验。
3. `V8.4.0`：已完成身份、组织分类和教师申请审核。
4. `V8.4.1—V8.4.2`：已完成教师建课、管理员审核和可见回执。
5. `V8.4.3`：已完成学生选课、教师审批和课程名单；`V8.4.4` 已完成共享草稿、教师可见结构化编辑器、不可变发布和三种学习完成预设。
6. `V8.4.5`：已完成三角色聚合读取、三种可见首屏和主要业务跳转，P-11 已迁移。
7. `V8.4.6`：当前先建立完整演示数据，再完成全链路验收并迁移最终系统分层图。

### 0.3 八条不可破坏规则

1. **实验本体冻结**：正式目录中的 127 项活动默认不再调整页面结构、控制方式、动画、参数、求解器和实验内文案。
2. **只允许一个实验例外**：本轮只允许完成已经开发一半的 `engineering.robot-arm-ik`；其他新实验全部暂缓。
3. **课程不等于实验外壳**：课程负责组织内容和学习关系，实验继续以独立页面运行；课程只能通过稳定 `activity_key` 引用实验。
4. **没有精品与普通等级**：三星系、学科和现有活动统一进入通用目录，不再把某门内容定义为精品课、代表课或低等级课程。
5. **班级不是课程**：班级表示学生的行政组织身份；课程表示教师实际教授、学生实际加入的学习空间。
6. **课程信息和课程内容分离**：管理员审核课程名称、教师、学年和准入方式；教师发布章节、文本、实验、检查点和作业时不再经过管理员逐项审批。
7. **发布必须可追溯**：共享草稿可修改，已发布版本不可修改；发布新版本不能覆盖旧版本和旧学习事实。
8. **暂缓低可见投入**：微信小程序、服务器发布、竞赛材料、新实验扩充、生产级安全和极限性能优化均不进入当前周期。

1. **用户层级不自然**：现有页面容易让教师先理解学校、班级、课程对象和技术状态，再完成实际教学动作。
2. **班级承担过多职责**：行政班、课程授课范围、作业范围和证据范围混在一起，无法自然支持公开课程和无行政班学生。

4. **课程信息与知识内容混写**：当前课程对象不能清晰表达“管理员只审基础信息、教师持续更新教学内容”。
5. **课程成员闭环已接通**：BE-026 与 FE-040 已实现课程码发现、公开/限班申请、审批、批量加入、名单、退出和双视口可见回读；课程内容共享草稿、发布和教师可见编辑也已继续接通。

7. **内容版本方向已经纠正**：课程发布后所有 active 课程成员读取内部群组最新 binding，旧 release、binding、页面版本和学习事实永久保留；后续不得恢复行政班手动固定版本。

## 2. 新的产品层级与通用课程概念

本节冻结所有后续开发共同使用的用户语言。任何页面、接口或数据模型都不得重新把“星系目录中的活动”和“教师实际教授的课程实例”混为一谈。

### 2.1 统一产品层级

~~~text
星序 Astra
├── 内容目录
│   ├── 学习空间 / 星系
│   │   ├── 学科或方向
│   │   │   └── 学习活动 / 实验
│   │   └── 只负责发现、分类与引用
│   └── 现有 127 项活动统一进入目录
└── 授课课程
    ├── 由教师从现有目录中组织
    ├── 可由多名教师共同管理
    ├── 可供多名学生独立加入
    ├── 包含章节、文本、实验、检查点和作业
    └── 通过发布版本向课程成员生效
~~~

例如数学教师可以建立“数学—小明老师—2026 学年高中版”。它可以默认归类到“工科试验室—数学”，但课程内容仍可引用其他学科或星系的活动。分类用于发现和筛选，不作为限制教师编排的硬墙。

### 2.2 核心术语

| 用户术语 | 技术对象 | 负责什么 | 不负责什么 |
| --- | --- | --- | --- |
| 学习空间 / 星系 | `LearningSpace` | 聚合工科、代码、未来星系内容 | 不授予课程编辑权 |
| 学科 / 方向 | 目录元数据 | 对活动和课程提供筛选 | 不决定学习关系 |
| 学习活动 / 实验 | `activity_key` 与活动目录 | 独立运行的互动内容 | 不保存课程名单 |
| 授课课程 | `Course` | 表示教师实际教授的一门课 | 不等同于某个实验页面 |
| 共同教师 | `CourseCollaborator` | 共同编辑、发布、审批学生 | 不形成上下级教师 |
| 行政班 | `ClassGroup(kind=homeroom)` | 表示学生所属班级身份 | 不自动等同于课程 |
| 课程内部群组 | `ClassGroup(kind=course_cohort)` | 兼容作业和学习证据范围 | 不向用户显示为行政班 |
| 课程成员 | `CourseEnrollment` | 表示学生实际加入课程 | 不要求一定存在行政班 |
| 课程信息修订 | `CourseInformationRevision` | 保存待管理员审核的课程信息 | 不保存教学正文 |
| 共享草稿 | `Course`、`CourseUnit`、`ContentDraft` | 保存教师当前编辑内容 | 不直接向学生生效 |
| 发布版本 | `CourseRelease` | 冻结学生实际读取的内容 | 发布后禁止修改 |

### 2.3 课程信息与课程内容分离

| 范围 | 示例 | 谁能修改 | 是否需要管理员审核 |
| --- | --- | --- | --- |
| 课程信息 | 名称、共同教师、学年、上课时间、总课时、星系、学科、准入方式、允许班级 | 课程教师提出修订 | 是 |
| 课程内容 | 章节、正文、实验选择、顺序、检查点、作业和完成规则 | 任一有效共同教师 | 否 |

首次课程信息通过后生成课程码和课程内部群组，但不伪造空白初始版本；尚未发布时统一显示“暂无已发布内容”。教师在 V8.4.4 完成至少一个课程单元和完成规则后显式生成首个不可变版本。后续信息修订等待审核时，旧的已批准信息继续生效；修订被拒绝时也不得影响正在运行的课程。

课程内容不采用管理员逐单元审核。任何有效共同教师都可以编辑同一份共享草稿，并通过明确的“发布”动作生成下一个不可变版本。

### 2.4 班级与课程的关系

1. 学生可以属于一个或多个行政班，也可以暂时没有行政班。
2. 学生可以加入多门课程；加入关系由 `CourseEnrollment` 表达。
3. 课程可以限制只有指定行政班成员申请，也可以向所有学生开放申请。
4. 教师可以一键把某个行政班的全部有效学生加入课程。
5. 课程名单必须显示学生当前行政班；无班级时显示“未关联班级”。
6. 作业、提交和学习证据继续需要 class scope 时，统一使用课程内部群组，不把行政班重新变成课程容器。

### 2.5 教师身份申请

正式角色继续只有 `student`、`teacher`、`admin`。申请教师不是第四个角色，而是普通账户叠加一条 `TeacherApplication` 状态：

- `pending`：只能预览正式发布内容，不能加入班级、课程或产生学习进度。
- `approved`：用户角色提升为 `teacher`，教师工作台解锁。
- `rejected`：账户恢复普通学生能力，可以重新提交申请。

公开界面不再直接创建正式教师。现有测试、初始化器和管理员创建正式教师的兼容入口继续保留，避免破坏已有自动化。

### 2.6 多教师协作

1. 创建者在课程草稿中选择共同教师。
2. 课程提交审核后，在所有共同教师工作台可见。
3. 所有有效共同教师都能编辑共享草稿、发布版本、审批学生和批改作业。
4. 课程信息中的教师名单变更必须建立新的 `CourseInformationRevision` 并由管理员审核。
5. 内容发布不要求创建者单独确认，也不建立“主讲教师高于协作教师”的复杂层级。

### 2.7 课程准入

课程只提供两种教师可理解的准入方式：

| 模式 | 学生入口 | 资格判断 | 最终处理 |
| --- | --- | --- | --- |
| 公开申请 | 输入课程码或从课程目录发起 | 所有普通学生都可申请 | 任一课程教师批准或拒绝 |
| 指定班级 | 输入课程码或班级课程入口 | 必须是允许行政班的有效成员 | 任一课程教师批准或拒绝 |

管理员具有兜底治理能力，但正常教学流程不要求管理员处理每一位学生的课程申请。

### 2.8 三种完成规则

教师创建课程单元时只选择三个直白预设，并为需要目标的预设明确选择一个检查点或一份作业：

1. **完成实验操作**：学生在该单元引用的正式活动运行时中产生一次由服务端接收的 `attempted` 操作事实；普通接口伪造的无运行时事件不计入完成。
2. **通过检查点**：教师选择该单元中的一个 inline `checkpointKey`，学生答案由服务端依据当前不可变内容版本判分，首次正确后完成。
3. **提交并完成批改**：教师选择该单元中的一个有效 `assignmentId`；学生提交后，课程教师把它批改为 `graded` 或 `returned`，且已经给出评分或反馈时完成。

前端不能直接写“已完成”。`LearningEvidenceEvent` 与 `Submission` 继续复用，`CheckpointAttempt` 按 Q-003 方案 A 新增为轻量、不可变检查点事实；当前真实投影类 `LearningActivityProjection` 只负责汇总展示。question-set 检查点在没有受信题库判分器前不得成为完成目标。

| `checkpoint_passed` | 新增 append-only `CheckpointAttempt` | 当前 release、指定 inline `checkpointKey`、未超过 `maxAttempts` 且服务端判分正确 | 把标准答案发给学生；客户端上报 `is_correct`；question-set 冒充已判分 |
| `assignment_reviewed` | 既有 `Submission` | 指定作业的提交由课程教师批改为 `graded` 或 `returned`，并已产生评分或反馈 | 学生提交即完成；非课程教师为隐藏课程群组批改 |

正确检查点和符合条件的作业批改在各自原事务内追加 `trusted_assessment / completed` 证据；实验操作由规则根据 runtime attempted 派生 `rule / completed`。三条路径最终只通过 `LearningActivityProjection` 回读，不建立第二套进度表。

#### 9.4.4 模型、接口与验证

- 新增模型：`CheckpointAttempt`；迁移 `20260825_0058_course_completion_presets` 接续 `20260825_0057`，当前保持唯一 Alembic head。
- 扩展 schema：`CourseUnitCompletionV1`、`CompletionActivityRule` 的 preset/目标字段和检查点提交 DTO。
- 新增接口：`POST /api/v1/courses/{course_id}/units/{unit_id}/checkpoints/{checkpoint_key}/attempts`；请求携带当前 `course_release_id`、稳定 `client_attempt_id` 和结构化回答，响应不返回标准答案。
- 复用接口：课程草稿/发布、正式活动 runtime、作业提交/批改、学习恢复/教师聚合和投影重建接口保持原路径。
- 必测：三种规则各自完成与未完成、无 runtime 伪造、错误/超限/重复检查点、旧 release、错误目标、越权批改、重复批改、规则复用/变更、事务回滚和投影删除后重建。

### 9.5 发布规则

以下规则已由 BE-027 落地，FE-041 必须直接消费，禁止建立前端私有发布真值：

1. 任一有效共同教师可以发布。
2. 保存和发布必须携带预期草稿 revision；旧 revision 返回 `409` 和当前代际提示。
3. 发布冻结精确页面版本、单元顺序、活动 key、媒体摘要和完成规则快照。
4. 新 release 建立后，为课程内部群组追加下一条 binding revision。
5. 学生下次读取课程时得到最新 binding，检查点答案字段由服务端移除。
